Zenodo 简介称 285,919 个订单、219 家客户。直接审计六份文件得到 285,941 行、24,532 个订单 ID、238 个客户 ID。[作者的预处理脚本](https://github.com/Infraste03/B2B-Parts-Rec/blob/main/create_splits.py)按每个客户至少 3 行筛选。原始文件中有 16 个客户各 1 行、3 个客户各 2 行，剔除这 22 行后，恰好是 285,919 行、219 个客户。因此简介中的“订单”很可能指筛选后的明细行，不能用于 `ORDER_ID` 的不同值计数。全部 24,532 个订单 ID 只对应一个客户和一个日期，其中 15,085 个订单 ID 对应多个物料 ID，说明数据适合从订单和订单明细两个层次建模。字段定义见[作者仓库的数据字典](https://github.com/Infraste03/B2B-Parts-Rec)。

本项目商业分析保留全部 238 个客户。219 个客户的筛选口径仅用于与作者的推荐系统实验对照。订单 KPI 使用 `COUNT(DISTINCT ORDER_ID)`，明细行 KPI 使用 `COUNT(*)`，两者分别标注。

## 第一项业务分析：客户再次采购

“再次采购同一物料”定义为同一客户与物料组合在至少两个不同的匿名日期出现。SQL 先按客户和物料分组，再统计不同请求日期。这一口径避免把同一订单内重复的明细行、或同一天多个订单，直接判为之后再次采购。

在全部 238 个客户的原始数据中，共有 73,020 个客户与物料组合。其中 34,664 个出现在至少两个不同日期，占 47.47%。173 个客户至少有一个这样的组合。另一种按不同订单与物料组合计算的口径，共有 221,886 组，其中 146,453 组发生在该客户第一次请求该物料的日期之后，占 66.00%。这两种比例分母不同，报表必须分别命名。

日期经过匿名化平移，时间间隔只能解释为数据集内的相对顺序。数据没有数量，因此这里的“需求”指请求记录或不同订单与物料组合的出现次数，并不等于采购件数。

## 字段与能回答的问题

主要字段有 `ORDER_ID`、`CUSTOMER_ID`、`REQUEST_DATE`、`ITEM_ID`、`PROJECT_ID`、`LINE_ID`、`MACHINE_ID`、`PRODUCT_MODEL_ID`、`LOCATION` 和 `PRICE_EXACT`。另有四列描述向量，它们是编码后的数字数组，无法直接作为人类可读的物料名称或机器名称。

可以计算不同订单数、明细行数、活跃客户数、不同物料数、客户再次采购同一物料的比例、客户与物料的采购间隔，以及匿名时间轴上的需求变化。这些指标需要明确采用原始行、去重行还是订单层次；当前报表保留原始行并标注口径。

数据没有采购数量、订单总金额、货币、交付日期、供应商、库存或真实国家。`PRICE_EXACT` 是单价，因此不能将它求和当作采购额，也不能计算采购总量、真实销售额、交付准时率、库存周转或供应商表现。跨地区单价比较也需要先确认货币和定价口径。

## 审计后的处理决定

项目保留六份原始 CSV 和完全相同的明细行，在本地数据库记录原始文件名与行号。订单、客户、物料和再次出现等核心指标采用明确的去重单位，避免把重复行误认为采购数量。只有需要展示原始行数时才直接计数明细，并在图表中标为“原始明细行数”。

四页 Power BI 报表、指标字典及业务结论已经完成，分别见[仓库首页](../README.md)、[指标字典](kpi-dictionary.md)和[项目结论](final-report.md)。[复现说明](reproduce.md)给出从 Zenodo 校验文件到重新生成汇总 CSV 的流程。原始 CSV 始终留在被 Git 忽略的本地目录。
